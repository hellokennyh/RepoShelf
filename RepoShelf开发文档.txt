# GitHub Project Library V1

## Antigravity 自主开发规格与验收文档

---

# 0. 任务目标

开发一个本地优先的 GitHub 开源项目发现、搜索和收藏桌面工具。

核心使用场景：

1. 浏览 GitHub 当前热门项目；
2. 根据关键词或自然语言搜索 GitHub 项目；
3. 将感兴趣的项目收藏到本地 SQLite 数据库；
4. 对收藏项目进行分类、标签、评级和备注管理；
5. 本地搜索和浏览收藏；
6. 不定期从 GitHub 刷新项目基础信息；
7. AI 为可选增强能力，不得成为软件正常运行的前置条件。

工作名称：

`GitHub Project Library`

V1 是一个个人桌面工具，但架构必须适合未来在 GitHub 开源，其他用户安装后使用自己的 GitHub Token、AI Provider 和本地模型。

---

# 1. 最重要的产品原则

## 1.1 Local First

所有收藏信息、评级、备注、标签和配置默认保存在本机。

不建立：

* 云端账号系统；
* 云数据库；
* 后台 SaaS；
* 用户注册登录；
* 项目同步服务器。

---

## 1.2 AI Optional

软件必须有两个逻辑运行层级：

### Basic Mode

完全不配置 AI Provider 仍然可以完成：

* GitHub Trending；
* GitHub关键词搜索；
* Star筛选；
* 最后活跃时间筛选；
* 搜索结果数量限制；
* 排除历史入选项目；
* 排除已收藏项目；
* 添加 GitHub URL；
* 收藏；
* 分类；
* GitHub Topics；
* 本地标签；
* 本地项目浏览；
* Rating；
* Notes；
* 删除收藏；
* 刷新 GitHub 项目信息。

### AI Enhanced Mode

只有 AI Provider 已正确配置时额外开放：

* 自然语言搜索理解；
* 搜索关键词扩展；
* 生成 GitHub Search Query；
* 简单 Category 建议；
* 简单 Tags 建议。

AI 不允许成为任何 Basic Mode 功能的依赖。

---

# 2. V1 明确不实现的功能

严格控制 Scope。

以下功能全部属于 V1 Non-Goals：

* Clone GitHub Repository；
* Git pull / fetch / checkout；
* 修改 GitHub Repository；
* Issue 管理；
* Pull Request 管理；
* GitHub Actions；
* Repository 写操作；
* 自动安装开源项目；
* 自动运行开源项目；
* Dependency 分析；
* 漏洞分析；
* 源代码深度分析；
* README 深度 AI Research；
* Issues/PR AI 分析；
* AI 项目评分；
* AI 项目对比；
* AI 推荐系统；
* 自动监控 Repository 更新；
* GitHub Star 双向同步；
* MCP Client；
* GitHub Official MCP；
* 第三方 Trending MCP；
* 云端同步；
* 多用户；
* 浏览器自动化；
* 自动更新程序；
* 插件市场。

不要因为“以后可能有用”而提前实现。

# 3. 推荐技术栈

## Desktop

Tauri 2

## Frontend

* React
* TypeScript
* Vite
* Tailwind CSS

避免引入重量级 UI 框架。

允许使用少量成熟 UI primitives，但不要为了 UI 引入庞大依赖。

## Backend

Rust

主要负责：

* GitHub API；
* GitHub Trending；
* SQLite；
* AI Provider；
* Settings；
* Secure Credentials；
* 网络错误处理；
* Rate Limit；
* 数据转换。

## Database

SQLite

## HTTP

Rust `reqwest`

## Serialization

`serde`
`serde_json`

## HTML parsing

Rust `scraper` 或等价成熟库。

## SQLite

优先：

`sqlx + SQLite`

使用 Migration。

## Secrets

不得将以下数据以明文写入 SQLite / JSON / Git：

* GitHub Token；
* OpenAI API Key；
* Anthropic API Key；
* Gemini API Key；
* Custom API Key。

优先使用操作系统 Credential Store。

如果采用 Rust：

优先考虑成熟的跨平台 `keyring` 实现。

如果实现过程中发现兼容性问题，可以改用 Tauri 官方安全存储方案，但禁止将密钥退化为普通 JSON 明文保存。

# 8. Trending 页面行为

UI：

```text
GitHub 热门项目

时间：
[ Today ▼ ]

可选：
Today
This week
This month

返回数量：
[ 20 ]

[获取热门项目]
```

返回数量建议：

```text
10
20
30
50
```

也可以允许用户输入整数。

但是：

GitHub Trending 本身返回多少项目取决于 GitHub。

如果用户要求 50，但 GitHub 当前只提供 20：

返回 20。

不要：

* 自动寻找其他来源补足；
* 重复结果；
* 使用 GitHub Search 伪造 Trending；
* AI 生成项目。

UI应提示：

```text
当前数据源只返回了 20 个热门项目。
```

# 9. Trending 排序

严格保持 GitHub Trending 官方顺序。

即：

```text
GitHub Rank 1
GitHub Rank 2
GitHub Rank 3
...
```

不要再二次按照：

* 总 Stars；
* AI评分；
* 更新时间；

重新排序。

GitHub Trending Rank 即 V1 的“热门程度”。

# 11. Trending REST Enrichment

Trending 页不一定包含所有需要字段，因此获取 Trending 后可以对项目调用 GitHub Repository REST API 补充 Metadata。

必须：

* 控制并发；
* 最大建议并发 4；
* 正确处理 GitHub Rate Limit；
* 单个项目补充失败不能让整个 Trending 页面失败。

例如第 7 个项目 REST 请求失败：

仍然显示该项目。

缺失字段显示：

```text
Unknown
```

而不是丢弃整个 Repository。

---

# 12. Trending HTML Parser 边界

GitHub Trending 没有稳定正式 REST Trending API，因此 HTML Parser 是潜在易变组件。

必须：

1. Parser 与业务逻辑隔离；
2. 使用 Fixture Test；
3. Parser 失败必须返回明确错误；
4. 不允许 UI 出现空白页面；
5. 日志记录 Parser failure；
6. 不要把 CSS Selector 分散在多个文件。

建议：

```text
trending/
  provider.rs
  github_html.rs
  parser.rs
```

未来 GitHub HTML 变化只需要修改 Parser。

# 13. 模块二：搜索项目

搜索有两个模式。

## Basic Search

## AI Search

```text
● 关键词搜索
○ AI自然语言搜索
```

```text

```

置灰或明确提示。

---

# 14. Basic Search

用户输入：

```text
instagram scraper
```

其他筛选条件：

### 最低 Stars

```text
不限制
或整数 >= 0
```

### 最后活跃时间

使用 GitHub：

```text
pushed_at
```

筛选：

```text
最近一周
最近一个月
最近半年
最近一年
不限制
```

转换成 GitHub Search：

```text
pushed:>=YYYY-MM-DD
```

### 返回结果数量

例如：

```text
10
20
30
50
100
```

默认：

20。

这是最终“入选项目数量上限”。

如果合格项目不足：

返回实际数量。

禁止凑数。

---

# 15. GitHub Search Query

示例：

用户：

```text
instagram scraper
```

条件：

```text
stars >= 100
最近半年活跃
```

构造：

```text
instagram scraper stars:>=100 pushed:>=YYYY-MM-DD
```

Search API 使用 GitHub Best Match。

不要默认：

```text
sort=stars
```

否则会降低相关度。

---

# 16. Basic Search 排序

优先保持：

```text
GitHub Best Match
```

在同等或非常接近的结果情况下使用：

```text
Stars
```

作为二级排序信号。

V1 不需要复杂数学 Ranking Algorithm。

---

# 17. AI Search

AI V1 只负责：

```text
自然语言
    ↓
搜索意图
    ↓
GitHub Search Queries
```

不要负责：

```text
搜索全部结果
    ↓
逐项目读取README
    ↓
逐项目AI审核
```

禁止两阶段 LLM Re-ranking。

---

# 18. AI Search 示例

用户：

```text
找可以获取 Instagram 粉丝和评论的开源项目，
最好提供API或者MCP，最近仍然有人维护。
```

AI只需要返回结构化结果，例如：

```json
{
  "queries": [
    "instagram scraper followers comments",
    "instagram api scraper",
    "instagram mcp"
  ],
  "suggested_category": "Automation"
}
```

最多生成：

3 个 GitHub Search Query。

一次 AI 调用完成。

---

# 19. AI Search 的低成本多查询策略

为了提高 Recall，同时避免逐项目消耗 AI Tokens：

AI一次生成：

```text
Query A
Query B
Query C
```

后台依次调用 GitHub Search。

合并结果。

按：

```text
github_repo_id
```

优先去重。

没有 ID 时：

```text
canonical github_url
```

去重。

最多获取满足最终要求所需的候选数量。

不要无限翻页。

建议候选上限：

```text
max(user_result_limit * 3, 100)
```

并设置硬上限：

```text
300
```

达到硬上限仍不足时直接返回实际结果。

---

# 20. 多查询结果排序

无需 AI。

如果只有一个 GitHub Query：

保持 GitHub Best Match 顺序。

如果多个 Query：

允许使用简单 Reciprocal Rank Fusion（RRF）合并排名。

例如：

```text
RRF score = Σ 1 / (60 + rank)
```

Stars 只作为 tie-breaker。

不要构建复杂 Recommendation Engine。

# 23. 排除后的补充搜索

例如：

用户要求：

```text

```

第一页得到20个。

其中：

```text

```

后台可以继续获取下一页，尝试补足20个。

但必须设置候选硬上限。

不要为了强行达到20个无限分页。

# 24. Selection History 写入规则

搜索完成并准备在 UI 展示最终结果时：

将这些“实际入选结果”写入：

```text

```

不是只有收藏后才写。

这正是：

```text
排除以前入选项目
```

的数据基础。

# 42. Refresh 并发

限制并发。

建议：

```text

```

必须展示：

```text

```

```text

```

# 43. 删除收藏

支持：

```text
删除收藏
```

只删除本地数据。

绝对不能：

* Unstar GitHub；
* 删除 GitHub Repository；
* 修改 GitHub。

删除收藏时：

cascade 删除对应：

```text
favorite_tags
```

selection_history 保留。

因为：

```text

```


---

## favorites

```sql
CREATE TABLE favorites (
    id INTEGER PRIMARY KEY AUTOINCREMENT,

    github_repo_id INTEGER UNIQUE,

    github_url TEXT NOT NULL UNIQUE,

    name TEXT NOT NULL,

    description TEXT,

    category TEXT NOT NULL DEFAULT 'Other',

    stars INTEGER NOT NULL DEFAULT 0,

    license TEXT,

    pushed_at TEXT,

    rating INTEGER
        CHECK (rating IS NULL OR rating BETWEEN 1 AND 5),

    notes TEXT NOT NULL DEFAULT '',

    favorited_at TEXT NOT NULL,

    metadata_refreshed_at TEXT NOT NULL
);
```

时间统一存：

```text
UTC RFC3339 / ISO-8601
```

UI负责本地时间显示。

# 45. favorite_tags

```sql
CREATE TABLE favorite_tags (
    id INTEGER PRIMARY KEY AUTOINCREMENT,

    favorite_id INTEGER NOT NULL,

    tag TEXT NOT NULL COLLATE NOCASE,

    source TEXT NOT NULL
        CHECK (source IN ('github', 'ai', 'user')),

    FOREIGN KEY (favorite_id)
        REFERENCES favorites(id)
        ON DELETE CASCADE,

    UNIQUE (favorite_id, tag, source)
);
```

# 93. Autonomous Agent Rules

Antigravity执行过程中必须遵守：

### Rule 1

不要扩大 V1 Scope。

### Rule 2

如果存在多个合理实现：

优先选择：

```text
简单
稳定
成熟依赖
低维护成本
```

而不是技术炫技。

### Rule 3

不要为了减少代码重复过早引入复杂抽象。

只有：

```text
GitHub Provider
Trending Provider
AI Provider
```

等明确未来扩展点需要抽象。

### Rule 4

外部 API 必须可以 Mock。

### Rule 5

不要测试真实付费 AI API。

### Rule 6

如果官方文档与本规格技术细节冲突：

可以根据当前官方 API 修改实现细节。

但不能修改产品行为或 Scope。

### Rule 7

遇到无法确定的外部 API 行为：

查官方文档或实际进行无破坏验证。

不要凭模型记忆猜。

### Rule 8

不要因为一个网络请求失败而删除已有本地收藏数据。

### Rule 9

所有数据库变更使用 Migration。

### Rule 10

每个阶段完成：

```text
run tests
review diff
commit
```

再进入下一阶段。

```text
1. 功能正确
2. 数据安全
3. Basic Mode完整
4. 本地数据库稳定
5. GitHub API稳定
6. 可维护
7. UI易用
8. AI增强
9. 扩展能力
```

AI不是核心。

MCP不是核心。

GitHub数据发现 + 本地收藏管理才是核心。

```text
small
reliable
local-first
AI-optional
open-source-friendly
```

的 GitHub Project Library V1。
